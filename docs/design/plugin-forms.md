# 插件形态能力矩阵

状态：2026-11-23。**未实现**标记的条目只有设计意图，没有代码。

范围：树内/树外开发者写插件时的四种载体（编译进主程序、动态库、Lua、WASM），
各自能挂哪些扩展点、能拿什么数据、配置怎么声明。存储原则见
[acb-policy-store.md](acb-policy-store.md)，本文不重复。

---

## 1. 目标

**任何一处有差异化需求的地方，都能隔离成插件，维护在树外**，不必改 ACB 本体。

判定「够不够」的三条硬标准：

1. 树外开发者能写一个插件，**不改 ACB 代码**就挂上某个扩展点；
2. 插件的**配置能由 ACB 控制台渲染**，不需要插件自带前端；
3. 插件的**数据可以自己管**（外部服务，或 ACB 库里的自有表）。

---

## 2. 现状矩阵

`✅` 已实现并有测试；`⚠️` 部分实现；`❌` 未实现。

| 能力 | 编译进主程序 | 动态库（.so） | Lua | WASM |
|---|---|---|---|---|
| 载体形态 | Rust crate | cdylib + C ABI + JSON wire | `.lua` 脚本，`mlua` 运行时 | `wasmi` 模块 |
| 树外可写 | ❌ 要改本体 | ✅ | ✅ | ⚠️ 宿主没接进内核 |
| 扩展点数量 | 17 / 17 | 17 / 17 | **8 / 17** | ❌ 0 |
| ABI 版本化 | 不适用（同源编译） | `ABI_VERSION` v1 / v2 | 跟随插件 API | ❌ 无 |
| 沙箱隔离 | 无（同进程） | 无（同进程，C ABI） | ✅ VM 沙箱 | ✅ 最严 |
| 数据访问 | 全库（同进程） | ❌ 只有 event/stop/log | ❌ 只读宿主给的结构 | ❌ 无 |
| 配置声明 | 无约定 | `options: Value`（自由 JSON） | 宿主给的表 | `decide(request)` |
| 配置渲染 | ❌ | ⚠️ `SchemaField[]` → JSONForms + 资源记录/动作按钮 | ❌ | ❌ |
| 自有数据表 | ✅ 直接写 | ❌ | ❌ | ❌ |

### Lua 支持的 8 个扩展点

`Wake` `Access` `Delivery` `Send` `TurnError` `Clock` `Receive` `Route`

**缺的 9 个**：`ToolAccess` `Observer` `Tool` `Task` `Prompt`
`PlatformAdapter` `Ticket` `Manager` `Loader`

### 树外 Rust 开发者的 SDK 缺口

`crates/adapter-api` 没有 `publish` 配置，树外只能靠 git 依赖或抄源码——**没有语义化
版本的契约**，ABI 一变插件就失效。

### 3.1 已就位的部分（别重复造）

`plugin_records` / `plugin_secret_refs` / `plugin_config` 三张表、`acbctl plugin`
子命令、控制台按 schema 渲染的表单与资源/动作面板、示例插件

（嵌套、联合类型、条件显示），不是「没有配置渲染」。

## 4. 分层约定

四种载体**各自用各自的原生 ABI**，不硬套 C ABI——Lua/WASM 的价值就在沙箱，
统一成 C ABI 会把优势抵消。但**语义必须一致**：同一个扩展点在四种载体里
表达同一件事，能力差异见第 2 节矩阵。

| 层 | 契约 | 谁写 |
|---|---|---|
| 语义层 | 扩展点定义、wire 形状、错误码 | 全载体共用 |
| 传输层 | C ABI（动态库）/ Lua API / WASM ABI | 各自实现 |
| 声明层 | manifest、配置 schema、数据 schema | 全载体共用 |

## 5. 目标形态（未实现，先记意图）

### 5.1 插件声明配置，ACB 渲染

现在插件给 `SchemaField[]`，前端翻译成 JSON Schema。目标改为**插件直接给 JSON
Schema 的一份子集**（对齐 OData 的元数据做法）：类型、必填、枚举、范围、默认、
分组、条件显示。控制台用 JSONForms 直接渲染，不再经过中间翻译。

### 5.2 插件自带前端

**两条路并存，默认走 5.1，例外走本条**（用户 2026-11-23 裁定 B）。

先弄清 dsh 的区别，别把两件事混成一件（我第一版混了，已改）：

| dsh 的机制 | 实际是什么 |
|---|---|
| `ctx.settings` 把 Config schema 投影成表单 | 配置页的**默认**做法 |
| `configure({ auto: false })` | 让这个实例**不出现在自动页面**里——是页面策略，不是「有没有前端」 |
| `dsh.client` + `exports["./client"]` | **整个 Web GUI 的通用扩展面**，插件自带构建好的 bundle，由宿主在 `/plugins/??<pkg>/client.js` 下拼接路由 |

所以 dsh 不是「配置页有两种写法」，而是「有一个通用前端扩展面，自动表单是它的
一个内置场景」。

ACB 要做的是同一件事的两个层次：

| 路径 | 插件给什么 | ACB 要做 | 用在 |
|---|---|---|---|
| **声明式**（PX5，默认） | JSON Schema 子集 | JSONForms 渲染 | 改配置就够——token、超时、枚举、范围 |
| **自带产物**（PX6，例外） | 构建好的静态目录 | 按插件 id 挂运行时静态路由 + 鉴权 | 图表、拖拽、实时预览这类自动表单表达不了的 |

**为什么保留声明式作默认**：强制插件为 3 个配置字段建一个 Vite 工程，成本远大于
收益；ACB 的插件主要是策略提供者（wake / access / clock），配置天然简单。

**ACB 与 dsh 的真实差异**：dsh 是 Node 进程，运行时直接读插件目录；ACB 的 web
产物是**构建期嵌入二进制**的（`console_web/app.js`）。所以要支持运行时插件静态
产物，得给静态服务加一条「运行时目录」路由——这是 PX6 的核心工作量，不是渲染。

### 5.3 插件自有数据

两条路都允许，由插件**初始化配置**选择：

- **外部**：插件自己连自己的库/服务，ACB 不管；
- **ACB 库**：插件声明数据形状，宿主建表、迁移、提供行级 CRUD ABI。

第二条需要先回答**迁移责任归属**（插件升版改列时谁负责迁移、失败怎么回滚），
这个问题没有答案之前不实现。

### 5.4 一等用例

以权限插件为试金石，至少要能写出：

- RBAC（角色 + 指派）；
- RBAC with scope（角色在房间/连接范围内生效）；
- 委托外部（OPA / Cedar）。

这三者共用 `ExtensionPoint::Policy`，数据存哪由插件自己定。

## 6. 推进顺序

1. 本文件（能力可见）；
2. `adapter-api` 可发布 —— 树外 Rust 插件有稳定依赖；
3. `ExtensionPoint::Policy` —— 权限模型可插件化，验证扩展点机制；
4. Lua 补齐 9 个扩展点；
5. 配置改成 JSON Schema 子集 + 插件自带前端通道；
6. `HostV1` 加 storage ABI —— 需先定迁移责任；
7. WASM 接入内核。
