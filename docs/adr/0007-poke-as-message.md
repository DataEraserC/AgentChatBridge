# ADR-0007 拍一拍是普通的平台事件

来源：用户裁定（旧实现缺陷由用户指出并要求纠正；「合并到统一逻辑」由用户于 2026-10-25 提出）。

## 这条决定了什么行为

拍一拍没有特殊逻辑，它就是类型为 `poke` 的平台事件，走[平台事件](0005-platform-events.md)的同一条路：

1. 归档成一行可读正文（如「[拍了拍我]」）进流水；
2. 过接收策略定是否算未读，算的话下一轮投递时 agent 看得到「谁在什么时候拍了谁」；
3. 唤醒策略想为它叫醒，就配一条按 `poke` 类型匹配的唤醒条件。**默认唤醒策略包含 `poke`**（来源：用户裁定，2026-10-25）——被拍了默认会醒；不想醒的订阅显式关掉。无论醒不醒，**永远不阻止记录**。

## 不这样会怎样

旧实现的缺陷：没有未读时拍一拍直接被吞——「把人拍了，agent 不知道」；有未读时投出去了，对话记录里也没有「谁拍的」。给拍一拍单开一条处理路径则要维护两套判定，行为迟早分叉——统一后核心只有一条路。

## 技术细节

拍一拍事件带谁拍的、拍了谁；「冲着我来的」由核心判定，供唤醒策略用。

## 2026-11-02 补充：拍一拍没有正文

拍一拍仍然归档成一行可读文本（`elements` 里的「[拍了拍我]」），但事件记录多了一个
`body` 字段，拍一拍标 `false`。这样唤醒策略能区分「只有触发、没有正文」和「事件本身
带来了信息」：前者可以延迟开轮等内容，后者（入群、上传、请求等）照旧立即处理。
描述文本还在流水里，`summary` 也保留；`body` 只影响 `Record::has_body()` 和唤醒判定，
不影响投递时给模型看到的内容。
