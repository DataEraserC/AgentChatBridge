# ADR-0035 房间候选取自「来过的消息」，输入需落库校验

来源：用户报障（2026-11-17）：`qqbot-official` 的房间选择只能手输，
「用户没办法很简单的看到」。用户裁定：
「自动维护有消息的群，用户可以手动输入，我们最终会确认一次，
若确实有这个群则把其加入到我们的维护列表并将用户输入的这个提交，
若没有这个群则报错，也不维护也不提交」。

## 这条决定了什么行为

房间候选有两个来源，**都能用**，且**都不需要适配器实现枚举**：

1. **见过的房间**：`records` 表里出现过消息的房间（`store.rooms()`）。
   平台适配器只要能收发消息，就自动攒出这张表——`qqbot-official`
   不提供枚举，但它收到的群消息会落库，于是它的群照样出现在候选里。
2. **适配器自报的房间**：实现了 `Outbound::list_rooms` 的适配器
   （目前 onebot11）给出「平台上有哪些房间」，包含**还没来过消息**的。

外加**手输**，并且手输要经一次确认——见下文。

## 问题：手输是唯一的兜底，但它是黑箱

ADR-0033 的降级设计是「不支持枚举就留手输框」。这个降级是对的，
但对用户名不友好：**他不知道该输什么、也不知道输对了没有**。

目前 `POST /api/config/patch` 的 `subscription` op 对房间 id 只是
字符串解析，不校验这个房间是否存在。输错了要等到第一条消息投递失败
才发现（或者永远不知道，因为那个群根本没人说话）。

## 决策一：候选 = 见过的 ∪ 适配器自报的

控制台 `/api/rooms?connection=X` 的响应增加 `seen` 段：

```json
{
  "connection": "qqbot-official",
  "supported": false,              // 适配器不实现枚举（保持不变）
  "rooms": [],                     // 适配器自报的（空）
  "seen": [                        // 来过消息的房间（新增）
    {"room": "qqbot-official:group/E1415...", "label": "", "messages": 5, "last_at": 1794888225460}
  ]
}
```

`seen` 与 `rooms` 分开而不是合并：
- `rooms` 的语义是「平台上有这些房间」（`supported` 决定它可不可信）
- `seen` 的语义是「这些房间确实有消息」，**与适配器能力无关**，永远可信

合并会让 `supported: false` 时连 `seen` 也被当成不可信——那正是现在
`qqbot-official` 用户遇到的困境。

`messages` / `last_at` 给用户判断依据：一个 5 条消息的群和一个 9832 条
消息的群，可信度不一样。

## 决策二：手输要确认，确认的后端是「查库」

用户输入房间 id 后，控制台先 `POST /api/rooms/verify`：

```
{"connection": "qqbot-official", "room": "group/E1415..."}
→ {"known": true, "messages": 5, "last_at": ...}   // 库里有
→ {"known": false}                                  // 库里没有
```

- `known: true` → 前端才允许提交订阅（`/api/config/patch`）
- `known: false` → **报错，不提交，也不加入维护列表**

这满足用户的三条要求：确认一次、有则提交、没有则报错且不落任何东西。

### 为什么校验在服务端而不是前端

前端比对 `seen` 也能做到，但：
- `seen` 是分页的（房间可能很多），前端拿到的不全
- 用户可能在另一个标签页刚收到消息，`seen` 是旧的
- 校验要与提交用**同一份数据源**，否则会出现「校验过了但提交时库变了」

所以校验是一次独立的后端查询，只读、无副作用。

## 决策三：不引入「维护列表」这个新概念

用户说的「加入到我们的维护列表」——**它已经存在了，就是 `records` 表**。

不需要新增一张表：房间一旦有消息就自动在 `store.rooms()` 里，
这本身就是「维护列表」。`/api/rooms/verify` 查的就是它。

好处：没有第二份真相源，不会出现「维护列表说有、records 表说没有」。
代价：一个从来没来过消息的房间（哪怕适配器枚举到了）在 `verify` 里
会显示 `known: false`。这是**有意的**——那种情况用户应该从 `rooms`
（适配器自报）里选，那条路径不需要 verify。

## 不做的事

- **不自动订阅**。见过消息 ≠ 想让它进会话。「自动维护」只到「候选可见」，
  订阅仍然是人的决定。
- **不清理 `seen`**。没有任何记录说「这个群没消息了就该从候选里消失」。
  真要清理让 retention 去处理 `records`，`seen` 自然跟着变。
- **不猜 label**。`qqbot-official` 的群没有群名可拿（官方 API 不给），
  `label` 就是空字符串。硬造一个「群 E1415…」是噪音。

## 验收标准

1. `qqbot-official` 连接下，`/api/rooms` 的 `seen` 里能看到
   `group/E1415AF6F62F025480ECDAFA1D4AC05C`（实测有 5 条消息）
2. `onebot11` 连接下，`rooms`（枚举）与 `seen` 都有内容，且不重复展示
3. 前端房间选择器：有 `seen` 就列出，无 `seen` 且 `supported: false` 才只给手输
4. 手输不存在的房间 → 报错，且 `config_objects` 里**没有**新增订阅
5. 手输存在的房间 → 确认后提交成功
6. `deploy/verify.sh` 全绿

## 已知代价

- `seen` 是按连接查 `records` 的 distinct，房间特别多时这个查询会慢。
  缓解：加 `LIMIT`（按 `last_at` 倒序取最近 N 个），不要求一次给全。
- 一个群只有机器人自己的消息时也算 `seen`（`records` 里有它的记录）。
  这是对的：那说明群是活的。
