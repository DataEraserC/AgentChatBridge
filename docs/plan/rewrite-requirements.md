## 1. 一句话

把聊天平台的消息可靠地交给 AI agent，把 agent 的动作可靠、受控地执行回聊天平台。

核心只懂「消息、会话、能力、调用、状态」，不懂 QQ 的群规则、不懂某个 harness 的
MCP 端口、不懂插件用什么构建。

---

## 2. 六条硬需求

| # | 需求 | 判据 |
|---|---|---|
| R1 | **harness 无关** | 不要求各 harness 有相同的插件 API / 工具机制；接新 harness 只需实现一份契约 |
| R2 | **平台无关** | 兼顾公共消息语义与平台特有能力；既不削成纯文本，也不把某平台写进核心 |
| R3 | **可扩展** | 支持 native / 动态库（.so/.dll）/ Lua / 外部进程；**插件管理器与加载器也允许第三方实现**，官方要给可运行的参考实现 |
| R4 | **减轻插件开发者负担** | 插件用自描述接口（类 OData）声明配置、资源、操作、状态；**ACB 前端自动生成常规配置与管理页**，插件不必自己写 |
| R5 | **可自迭代** | AI 改自己的代码 → 构建（可能依赖 nix / 编译链）→ 升级 → **失败自动回退** |
| R6 | **操作系统无关** | Linux / Windows 都能跑；**不依赖 nix / systemd**，但有它们时用其能力强化自己 |

## 3. 本轮新提的需求（2026-11-23）

| # | 需求 | 备注 |
|---|---|---|
| R7 | **插件热加载** | 改插件不重启桥，下一轮生效。配置热更新与代码热更新要分开定 |
| R8 | **插件管理页含启停** | 启用/停用、健康状态、失败原因、生效范围；停用后工具立刻从 agent 工具面消失 |
| R9 | **插件自带前端（例外）** | 默认配置页由 ACB 生成；需要图表/拖拽时允许插件带静态产物，ACB 挂运行时路由 |
| R10 | **插件数据自管** | 数据可存外部服务，也可存 ACB 库里的自有表；**表结构维护能力也要有** |
| R11 | **四种载体一等公民** | native / 动态库 / Lua / WASM 都要能挂扩展点，能力差异要公开 |

## 4. 文档要求（用户明确提过）

- 清晰、简洁、**分段**；一个文件/页面不塞大段内容。

## 5. 已知的设计张力（新分支必须先回答）

| 张力 | 说明 |
|---|---|
| **可扩展 vs 安全基础** | 授权、激活互斥、恢复日志不该被插件替换——核心要保留最终控制权 |
| **插件声明数据表 vs 迁移责任** | 插件升版改列时谁执行 `ALTER TABLE`、失败怎么回滚、表名冲突怎么办 |
| **不依赖 nix vs 用 nix 强化** | 同一条代码路径要能在「有 nix」和「无 nix」下都成立 |
| **自迭代 vs 回退** | 构建失败、升级失败、升级后起不来，三种情况的回退点不同 |
| **配置页自动生成 vs 插件自带前端** | 默认走生成；例外走静态产物，但 ACB 的 web 产物是**编译期嵌入二进制**的，要加运行时路由 |
