# 人机协作开发工作法

> 读者：项目所有者（不需要读代码）。目标：让 AI 产出**优雅且正确**的项目与代码。
> 依据：本仓库 2026-11 那 314 个提交的复盘（`docs/plan/full-review-20261109.md`）+ webmux 的工程实践。
> 一句话：优雅不是文风问题，是**约束问题**。

---

## 0. 先纠正一个误解

「AI 写的代码不够优雅」通常被归因于模型能力或提示词水平。真实原因几乎总是这四个之一：
**没给边界、一次改太多、改完没验证、它不需要维护**。

所以正确的做法不是找更会说话的提示词，而是**建一套它无法蒙混的结构**：
范围小到能一次看完、完成标准先写死、验收只能由命令给结论、每次踩坑转成一条守卫。
这套结构建好之后，换个更笨的模型也能出好活；结构没有，再聪明的模型也会攒出屎山。

---

## 1. AI 把项目写乱的四个机制

| 机制 | 具体表现 | 对策 |
|---|---|---|
| 上下文窗口有限 | 它只优化眼前这两百行，看不见「另一个文件里已经有一份同样的逻辑」 | 每个任务限定范围，先让它只读侦察并报告事实，再动手 |
| 没有维护痛感 | 复制粘贴比抽象便宜，它不会在下个月为这个选择付账 | 用测试与架构守卫代替自觉；守卫红了它就必须改 |
| 乐观偏差 | 会说「已测试通过」「应该没问题」 | **只认命令输出与退出码**，不认自述 |
| 一次做完的冲动 | 一个回合改 8 个文件、跨 3 个模块 | 一次一件事，diff 大到看不完就拆 |

对照一下我们真实发生过的事：8 天 314 个提交、415 个文件、没有一道门禁；
`docs/design/acb-policy-store.md` 2062 行，代码里 `PolicyStore` 零命中；
`HANDOFF.md:30` 写着「nix build 会自动跑 cargo test」，而 `flake.nix` 里是 `doCheck = false`。
这三件事都不是模型不会写代码，是**结构缺了三根柱子**：粒度、验收、事实来源。

## 2. 主循环：五步一收敛

```mermaid
flowchart LR
    A["① 需求卡<br/>目标 / 验收断言 / 不做什么"] --> B["② 只读侦察<br/>读哪几个文件<br/>报告事实，不改代码"]
    B --> C["③ 先立断言<br/>测试或命令<br/>红了才算写对"]
    C --> D["④ 最小实现<br/>一次一件事<br/>diff 可一次看完"]
    D --> E{"⑤ 机器验收<br/>命令 + 退出码"}
    E -- 通过 --> F["⑥ 收敛<br/>提交 + 更新文档<br/>把这次的坑写成守卫"]
    E -- 不通过 --> C
```

六步里最容易漏的是 **③ 先立断言** 和 **⑥ 收敛**：

- 没有 ③，你得到的是「能跑但不知道为什么能跑」的代码，下次改就塌。
- 没有 ⑥，同一个坑三个月后再踩一次——我们仓库里 `heal_own_holes` 这种「事故补丁」
  之所以要长期保留，就是因为根因没有变成断言。

## 3. 七条硬规矩（每条都配了我们的反例）

1. **一次会话只做一件事**。换任务就换会话。
   反例：一次重写覆盖 engine、adapters、安装链，事后没人能说清哪一段引入了哪个问题。
2. **先定义「怎么算完成」，再让 AI 写第一行代码**。断言可以是测试、可以是一条 curl、
   也可以是一个 grep，但必须是**别人能重跑**的。
   反例：`PolicyStore`、`ACB_KEY` 这些写进 ADR 的裁定，没有任何一条断言，于是永远停留在文档里。
3. **禁止 AI 自述验证**。它说「已通过」不算，贴命令与输出才算；
   如果它跑不了（沙箱限制），要求它明确写「未验证 + 原因」。
   反例：`HANDOFF.md` 里那句假事实，来源就是「有人以为 nix build 会跑测试」。
4. **先侦察，后动手**。让它在改之前先回答：涉及哪几个文件、现有实现长什么样、
   有没有已有测试看守。**不要相信注释**——注释会过期，代码不会。
   反例：我曾从注释推断「group 视图」是遗留坏味，实际那是有测试看守的既定设计。
5. **单次 diff 要能一次看完**。经验值：超过 300 行或 6 个文件就拆。
   看diff 不是为了看懂每一行，是为了在出问题时知道「嫌疑范围」。
6. **决策必须留痕，并标注是谁说的**。只有你亲口说过的才算「用户裁定」，
   AI 的推断一律标「实现默认」。这一条能防止 AI 把自己的偏好写成你的决定。
   反例：`docs/plan` 里 45 篇文档，如果分不清哪条是你定的、哪条是它猜的，就无法复核。
7. **核心不变量优先**。这个项目的核心承诺是「消息不丢、不重、不乱序」；
   任何改动如果动了水位 / ack / 串行，先补测试再改代码。代码风格永远排在后面。

## 4. 让输出变「优雅」的三个杠杆

**杠杆一：把边界写成硬规则。**
不是「注意分层」，而是「`adapters/*` 不许 `use acb_kernel::`，违反则测试失败」。
能执行的规则才会被遵守，写在文档里的规则只会被引用。

**杠杆二：给样板，不给形容词。**
「写得优雅一点」等于没说。「照 `crates/kernel/src/render.rs` 的结构写，命名跟它一致」
才是可执行的指令。AI 模仿具体文件的能力远强于理解抽象审美的能力。

**杠杆三：让反馈回路短。**
一条命令跑完所有检查（编译 + 测试 + 文档链接 + 端口/配置自检），失败就红。
回路越短，AI 越可能自己发现错误；回路是一堆散命令，它就会跳过。

## 5. 你不读代码，怎么判断这次改得对不对

**四个问题，问 AI 就够了**（它答不上来就说明这次没做完）：

1. 你跑了哪条命令？把输出贴给我。（不是「测试通过」，是原文）
2. 改了哪几个文件？各改了什么，一句话一个。（`git diff --stat` 一起贴）
3. 这次改动新增了什么守卫？如果没新增，为什么不需要？
4. 如果现在要回滚，怎么做？回滚会丢什么？

**下面这份验收清单，你只看得懂打勾就行：**

| 检查项 | 合格标准 |
|---|---|
| 命令可重跑 | 别人照着你给的命令能复现同样的结果 |
| 范围清楚 | 文件数与行数在预期内，没有顺手改无关文件 |
| 有断言 | 新增行为有测试或可复现的命令，且**先红后绿** |
| 事实一致 | 改完后文档里没有和代码矛盾的句子 |
| 可回滚 | 单次提交可单独 revert，不牵动别的改动 |

**三个追问句式**（专治含糊）：

- 「这条结论，你是读代码得出的，还是从注释/文档推断的？」
- 「如果这条不成立，会出现什么现象？我怎么自己验证？」
- 「你说完成了，完成的标准是谁定的？写在哪一行？」

## 6. 我们踩过的四个坑（留着当教材）

1. **314 个提交没有一道门禁**：代码其实是绿的（1080 通过），但没人知道，因为
   `nix build` 不跑测试、CI 只发文档站。**「能跑」和「知道它能跑」是两件事。**
2. **交接文档写了一个假事实**：`HANDOFF.md` 说 nix build 会跑测试，实际不会。
   文档不会自己变旧，是写它的人没有验证。
3. **2062 行设计文档 vs 0 行实现**：决策写得越漂亮，越容易让人以为已经做了。
   文档必须带状态：`草案 / 已接受 / 已实现 / 已废弃`。
4. **用注释代替读代码**：注释说「下一进程会接着处理」，代码里没有这段逻辑。
   凡是「承诺行为」的句子，都要能指出实现位置，指不出就是没有。

## 7. 提示词包（直接复制）

### P0 · 常驻约束（贴在每个新会话的第一条）

```text
你在为 <项目名> 写代码。仓库：<路径>。
先读仓库根的 AGENTS.md（若不存在，先读 README.md 与 docs/03-architecture.md）。

铁律：
1. 一次只做我这一条要求里的事，不要顺手重构、不要顺手改无关文件。
2. 动手前先只读侦察：告诉我涉及哪些文件、现有实现是什么样、有没有测试看守。
3. 先告诉我「怎么算完成」（可重跑的命令或测试），我确认后再改代码。
4. 不许说「已测试通过」而不贴输出；跑不了就写「未验证 + 原因」。
5. 任何结论必须给 文件:行号，不许从注释或文档推断实现。
6. 你做的决定标「实现默认」，只有我明确说过的才叫「用户裁定」。
7. 改完给我：改了哪些文件、验证命令与输出、还剩什么问题。
```

### P1 · 只读侦察（不许改代码）

```text
只读侦察，不要修改任何文件，不要跑构建。
目标：<要解决的问题一句话>。

请回答：
1. 这个问题涉及哪几个文件？各自的职责是什么（一句话）。
2. 现有实现是怎么处理的？贴关键代码 文件:行号。
3. 有没有测试/断言看守这个行为？列出来。
4. 你认为最小改动是什么？会牵动哪些不变量（数据/协议/并发）。
5. 有没有「文档说的和代码做的不一样」的地方？

不确定的地方明确写「不确定」，不要猜。
```

### P2 · 变更单（一页，写完停下等确认）

```text
基于刚才的侦察，写一张变更单，不要写代码：
- 要改什么（一句话）
- 验收断言（可重跑的命令/测试，写清期望输出）
- 不做什么（明确划出范围外）
- 风险：可能影响哪些不变量、哪些已有测试可能变红
- 回滚方式
写完停下，等我确认。
```

### P3 · 实现（先断言后代码）

```text
按变更单实现。顺序要求：
1. 先写能复现问题的断言（测试或命令），并给我看它现在是红的。
2. 再改代码让它变绿。
3. 每完成一小步报一次进度，不要一口气改完再汇报。
4. 如果中途发现变更单里有错，停下来说明，不要自行扩大范围。

结束时给我：git diff --stat、验证命令与完整输出、未验证的部分。
```

### P4 · 审查（交给外审 AI，建议用强推理模型）

```text
仓库只读。按 docs/plan/code-review-prompt.md 的提示词执行审查。
先读 docs/plan/full-review-20261109.md 作为已知事实基线，
只报那份报告之外的问题，或能推翻其中结论的证据。
每条发现必须给 文件:行号 + 触发条件 + 后果 + 建议方向 + 代价。
宁少而准，不许凑数。
```

### P5 · 收敛（每次改完都做，最容易被跳过）

```text
这次改动留下了哪些可复用的东西？逐条回答：
1. 有没有新的失败模式是我们之前不知道的？→ 要不要补一条断言？
2. 文档/ADR 里有没有因此过期的句子？指出位置。
3. 这次有没有违反分层/命名/依赖方向？如果有，是规则错了还是实现错了？
4. 用一句话总结「下次遇到同类问题的判断依据」，我把它写进 MEMORY。
```

## 8. 在 ACB 上怎么用

1. **先建门禁**：`deploy/verify.sh` 一条命令（测试 + 文档链接 + 配置自检）。
   没有它，下面所有步骤都是在沙子上盖楼。
2. **写 `AGENTS.md`**：把 P0 的铁律固化进去，控制在 200 行内；
   超了就把细则搬到 `docs/agent-rules/`，但不许删规则、不许抬上限。
3. **每个功能走 P2 → P3 → P5**：变更单是唯一入口，实现必须带断言，收尾必须留守卫。
4. **每周把「已接受但没实现」的文档清一次**：要么实现，要么降回草案。
5. **外审交给 P4**：它只提意见，通过与否看 `verify.sh`——AI 的意见永远不是门禁。

## 9. 一页速查

| 你现在的处境 | 用哪个提示词 | 你要看的证据 |
|---|---|---|
| 想动一个功能，但不知道会牵动什么 | P1 侦察 | 文件清单 + 现有实现位置 + 已有测试 |
| 方案还没定 | P2 变更单 | 验收断言写没写清、范围划没划出来 |
| 开始写了 | P3 实现 | 先红后绿的证据 + `diff --stat` |
| 写完了，心里没底 | P4 审查 | 有证据的问题清单，不是感想 |
| 上线前 | P5 收敛 | 新增守卫 + 过期文档位置 |
| AI 说「已完成」 | 追问三句式 | 命令输出，而不是形容词 |

---

## 10. 一句话记住

> **不要指望 AI 自觉，要让它无处可蒙。**
> 范围小、断言先行、命令说话、坑变守卫——这四件事做到，产出自然就优雅了。
