# 动态库调用超时与线程泄漏（设计，待拍板）

状态：只出设计，未改代码。
范围：`crates/adapters/dynamic/src/lib.rs` 的 `invoke_with_timeout` 及句柄生命周期。
相关常量：`CALL_TIMEOUT = 2s`（`lib.rs:58-60`）。

## 0. 结论摘要

| 方案 | 是否能回收卡死的插件线程 | 改动量 | 推荐度 |
|---|---|---|---|
| D. 超时后把句柄标死、后续快速失败 | 否，但泄漏被限制为每适配器 1 个线程 | 小 | **先做** |
| A. 每适配器单 worker 线程 + 有界队列 | 否，同上，但并发更可控 | 中 | 下一步 |
| B. 动态插件进程隔离 | 是（杀进程即可） | 大 | 不可信插件/强隔离时做 |
| C. 共享线程池 | 否，且会拖垮其它插件 | 中 | 不推荐 |

**推荐路径：先 D 止血，再评估 A；B 作为不可信插件或需要硬隔离时的中期方案。**

---

## 1. 现在为什么会泄漏

`invoke_with_timeout`（`dynamic/src/lib.rs:1932-1955`）每次调用：

1. `thread::spawn` 一个新线程；
2. 线程里拿 `Mutex<AdapterHandle>`，调用插件的 `invoke_fn`（C ABI，可能永不返回）；
3. 调用方 `recv_timeout(CALL_TIMEOUT)`；超时后返回错误，但**线程无法取消**。

后果：

- 每个超时的调用留下一个阻塞线程，并继续持有 handle 锁；
- 后续每个调用又 spawn 一个新线程，全部排在同一个锁上 → 线程数随调用次数线性增长；
- `destroy_handle`（`lib.rs:1969-1991`）等 2 秒拿不到锁就放弃，句柄永远无法清理；
- `UnloadSafeLibrary::unload` 要求先 destroy 所有 handle；在 destroy 放弃后再 `dlclose`，
  插件代码可能仍被卡住的线程执行，属于不安全的卸载路径（现有 loader 只能选择不 unload，
  库与句柄泄漏到进程退出）。

触发条件：插件实现有死循环/死锁/长时间阻塞（包括等待本应回调的 host 事件）。
这是插件 bug，但 core 目前会把「一次插件 bug」放大成「持续线程与句柄泄漏」。

---

## 2. 方案与代价

### D. 超时后句柄标死（最小止血）

做法：

- `AdapterHandle` 增加 `failed: bool`；
- `invoke_with_timeout` 超时后：置 `failed = true`，写 `lastError`/日志，返回明确错误；
- 之后所有 `send/call` 在拿锁前先看 `failed`，直接返回「适配器已失效」，不再 spawn 线程；
- `destroy_handle` 只在拿得到锁时 destroy；拿不到就把句柄记为不可回收，**跳过 dlclose**；
- 重启桥是唯一恢复方式（与当前注释一致）。

代价：每适配器最多泄漏 1 个线程 + 1 个库；不会再无界增长。
优点：改动约几十行，不动 ABI，不动配置；错误从「超时」变成「已失效」，语义更诚实。
缺点：适配器不能自愈；同一连接后续所有请求都失败，需要 supervisor 重启或人工处理。

### A. 每适配器单 worker 线程 + 有界队列

做法：

- 每个动态适配器一个 worker 线程，持有句柄并串行执行所有 `invoke`；
- 调用方把请求（id + 消息 + reply sender）放进有界队列，等 reply 或超时；
- worker 卡死时，队列变满；超时后标死适配器（同 D），但**不再创建新线程**；
- 一个适配器最多一个卡死线程；其它适配器不受影响。

代价：中等（约 1-2 天，含测试）；请求/回复通道与现有 `ProcessOutbound` 类似。
优点：线程数恒定；并发行为明确；为 B 的接口预留（worker ↔ 子进程可替换）。
缺点：仍然无法回收卡死线程；`dlclose` 依旧不安全，只能不卸载。

### B. 进程隔离

做法：把动态库放进外置进程（可复用 process 适配器的 wire），core 只通过 stdin/stdout
通信；超时 = kill 子进程 + 重启，线程/库随进程消失。

代价：大。需要解决：
- HostV1 回调（`submit_event`）跨进程转发；
- 动态 manifest / 方法目录的启动协商；
- 打包与部署（`.so` + 启动器）；
- 性能：每次调用多一次 IPC，平台事件多一次转发。

优点：唯一能真正回收卡死插件、并隔离内存破坏的方案；对不可信第三方插件是正确边界。
不适合当前「in-process 快速迭代」的阶段，适合作为插件分发/不可信插件的配套。

### C. 共享线程池

把调用丢进固定线程池，看似限制线程数，但卡死任务会永久占用池线程；多个坏插件会耗尽池，
拖垮所有动态适配器。不推荐。

---

## 3. 可观测性与失败语义

- 超时日志：连接/适配器 id、已等待毫秒、句柄状态（`failed`）；
- 控制台 `lastError`：与 `instantiate_errors` 并列，显示「动态适配器已失效，需重启」；
- 健康检查：该 provider `Unhealthy`；
- 重试语义：`failed` 后不再发起调用，避免 agent 反复重试放大问题；
- 卸载：拿不到 handle 锁时明确记录「库不可回收」，不执行 `dlclose`。

## 4. 测试

- 假插件 `invoke` 睡 10 秒：一次调用超时后 `failed = true`；
- 连续 100 次调用：不再 spawn 线程（线程数/调用次数断言或注入计数）；
- 失败后 `send/call` 立即返回明确错误；
- `destroy_handle` 在锁被占时超时返回且不 dlclose；
- 正常插件：D/A 不改变现有目录与调用行为（现有 conformance 测试保持通过）。

## 5. 需要拍板的点

1. 先做 D（推荐）还是直接上 A。
2. `failed` 后是否允许一次「重建适配器」（重新 `create` 新 handle）作为自愈，而不只靠重启桥。
3. 是否把 B（进程隔离）列为不可信插件的必要条件；若是，动态库 tool 载体 ABI 也应一并选型。
